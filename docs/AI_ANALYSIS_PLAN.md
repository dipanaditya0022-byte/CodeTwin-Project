# AI-generated code analysis: decision and test plan

24 November 2026 · phase 6

## Decision

CodeTwin does **not** offer an AI-generated-code check yet. Customers can run plagiarism analysis only; there is no "AI only" or "both" option. The feature is added only if a detector passes the acceptance test below, on data that looks like real lab work.

The reason is that no available method meets the bar a flag about a student needs. Shipping one now would put a number on screen that looks like evidence and is not.

## What the evidence says

* **Detectors are unreliable on code.** An evaluation of AI-content detectors on 5,069 code samples in an education setting found high false-negative *and* false-positive rates. Its conclusion was that existing detectors perform poorly at telling human from AI-written code ([Pan et al., "Assessing AI Detectors in Identifying AI-Generated Code: Implications for Education", arXiv 2401.03676](https://arxiv.org/html/2401.03676)).
* **Code is harder than prose.** Zero-shot detectors score how predictable each token is to a language model. Programming languages are so constrained that this signal is weaker for code ([arXiv 2506.06069](https://arxiv.org/html/2506.06069v1), which proposes a method built around that problem). It is a 2025 research result, not a validated tool.
* **Detectors are easy to evade.** For text, paraphrasing lowers every zero-shot detector's accuracy ([Fast-DetectGPT, arXiv 2310.05130](https://arxiv.org/pdf/2310.05130)). Renaming and restructuring do the same job for code, and students already do that.
* **False positives are what make or break a tool for teachers** ([arXiv 2510.25057](https://arxiv.org/pdf/2510.25057), on plagiarism detectors). Unlike a similarity flag, an AI flag has no second file to show. A student cannot answer it by pointing at evidence, only by asserting they wrote the code.
* Vendor blogs quote specific false-positive rates for commercial code detectors. They were not used here: they are marketing material and their sources could not be checked.

Scale makes this concrete. At a 2% false-positive rate, a lab of 60 honest students would produce about one wrong accusation per assignment. Short, standard exercises (sorting, binary search, matrix multiplication) are where human and AI code look most alike, and those are exactly the lab exercises CodeTwin is built for.

## Constraints from the design

* **Code stays in the tenant.** The design requires that student code never leaves the Azure tenant. That rules out hosted detection services and hosted LLM APIs. Any detector must run inside the worker.
* **Worker resources.** A token-probability detector needs a code language model in the worker: more memory and slower runs than UniXcoder embeddings. The size and cost would have to be measured first.
* **Never a verdict.** As for similarity, a score can only start a human review. It can never confirm a case.

## What CodeTwin already detects honestly

When several students paste output from the same assistant and prompt, their submissions often resemble each other. CodeTwin flags that as **shared code between students**, with the matching lines as evidence. It does not, and should not, claim the code was AI-written: the students may equally have shared a file with each other.

## Test plan (what would have to be true to ship it)

### 1. Data

A labelled set built for this purpose, separate from the plagiarism set:

| Part | Source | Size (minimum) |
|---|---|---|
| Human-written | real lab submissions from before widely available assistants (approved, roll numbers removed), plus solutions written under supervision | 600 files over 20+ problems |
| AI-written | the same problems, generated by at least three assistants, with several prompt styles (bare task, task + "write like a student", task + starter code) | 600 files |
| AI, edited | AI files after typical student edits: renaming, reformatting, removing comments, small logic changes | 300 files |
| Hard human | very short solutions, solutions following the teacher's starter code closely, and code by students who write comments in a second language | 200 files |

Splits are grouped **by problem and by generator**. A detector is always tested on problems and assistants it did not see.

### 2. Candidate methods, in the order to try them

1. **Zero-shot token probability with a small open code model run in the worker** (the approach of arXiv 2506.06069). No training data needed, but compute and memory need measuring.
2. **A classifier trained on the set above** (stylometric and token-probability features). Expected to do well on familiar problems and generators, and to be judged on unfamiliar ones.
3. **Not in scope:** keystroke or edit-history signals. They need an editor CodeTwin does not provide, and raise separate privacy questions.

### 3. Acceptance criteria

All must hold on the held-out split:

* **False-positive rate on human code ≤ 1%**, with the upper end of its 95% confidence interval ≤ 2%, overall *and* separately for the hard-human part
* recall reported for raw and edited AI code (no minimum: the point is to know it, not to promise it)
* no group of human authors (by problem, file length or comment language) with a false-positive rate above 2%
* results reproduced on a second, independent set of real submissions before any customer sees the feature

If no method passes, the outcome is reported, and the feature stays out.

### 4. If it passes: product rules

* off by default; the customer turns it on per assignment and chooses plagiarism, AI indicator, or both
* shown as an **"AI-likelihood indicator"**, never as "AI-generated", with the measured false-positive rate beside it
* shown only to the course owner; never to participants or students, never in the participant result view
* never creates or joins a review cluster by itself, and cannot be the reason given for a confirmed decision
* the model version and the score are stored with the run, as for similarity, so a result can be explained later

### 5. Effort

About 2–3 weeks: one to build and label the data, one to evaluate the two methods, and a few days for the product rules if a method passes. Collecting real human submissions needs the same approval as open question 4 in the design (use of real lab work, anonymisation).
